# T4 / T5 / T6 model, material and image structs: a cross-game reference

What E115 needs to read from OAT's in-memory zone structs to draw a static or skinned XModel with its materials, for
WaW (T4), BO1 (T5) and BO2 (T6). Researched 2026-10-26.

## Conventions

- **Path prefixes.** `OAT/` is `<OAT checkout>/src/` (the OpenAssetTools copy vendored in our b2w fork). `RE/` is the root of
  this repository (CoD-RE).
  - Headers: `T4H` = `OAT/Common/Game/T4/T4_Assets.h`, `T5H` = `.../T5/T5_Assets.h`, `T6H` = `.../T6/T6_Assets.h`.
  - Code: `XMC` = `OAT/ObjWriting/XModel/XModelToCommonConverter.cpp.template`, `PACK` = `OAT/Common/Utils/Pack.cpp`.
- **Status tags.**
  - **[V]** verified: read in the source at the given `file:line`.
  - **[V-calc]** verified by computing it. Offsets come from a ctypes replica of the OAT struct with 32-bit pointers.
    The T5/T6 values match `RE/shared/probe/sizes.txt` and the BO2 PDB figures in `RE/shared/notes/bo1_to_bo2_porting.md:183`.
  - **[I]** inferred, not checked against the game.
  - **[!]** the sources disagree, or there is a trap.
- **Offsets** are the 32-bit zone layout. OAT's loader fills native structs, so in E115 read the fields by name, not by
  offset. The offsets matter only for raw memory or `.ff` work.
- **CoD-RE headers.** `RE/games/t5-bo1/headers/T5_Assets.h` and `RE/games/t6-bo2/headers/T6_Assets.h` are copies of
  the OAT headers. Diffed with CRLF ignored, the only differences are an include path and the `FX_ELEM_TYPE` enum
  (from line ~5107 / ~5440 on), so every struct below is identical in both **[V]**. Line numbers below are OAT's.
  They match CoD-RE up to those points.

**Selecting a LOD.** LOD `n` uses `surfs[lodInfo[n].surfIndex .. surfIndex + numsurfs)`. Its materials are
`materialHandles[surfIndex + i]`. Source: `XMC:175-192`, `XMC:346-359` **[V]**. `numLods ≤ 4`.

### 1.3 Collision bits (not needed for rendering)

- **Layout.** `XModelCollSurf_s` is `{collTris*, numCollTris, mins[3], maxs[3], boneIdx, contents, surfFlags}`, 44 B
  in all three games. `XModelCollTri_s` is `{plane[4], svec[4], tvec[4]}`. Sources: `T4H:467-483`, `T5H:575-591`,
  `T6H:2755-2764`, `T6H:5763-5768` **[V]**.
- **Physics geometry.**
  - T4 holds it in `physGeoms` and `collmap` (each a `PhysGeomList {count, PhysGeomInfo*, PhysMass}`).
  - T5/T6 hold it in `Collmap {PhysGeomList*}[numCollmaps]`, where PhysGeomList is `{count, geoms, contents}`.
  - Sources: `T4H:540-545`, `T5H:653-663` **[V]**.
- **Per-surface trees.** The per-rigid-list `XSurfaceCollisionTree` (quantised AABB tree over the triangles) hangs off
  each `XRigidVertList`. It is layout-identical in all three games: `T4H:377-385`, `T5H:510-518`, `T6H:6944` **[V]**.
- **Fork export.** The vendored fork writes T4/T5 collSurfs to the model JSON losslessly
  (`OAT/ObjWriting/XModel/XModelDumper.cpp.template:396-427`, a "waw2bo2" fork addition) **[V]**.

**XSurfaceVertexInfo.**
- T4: `{int16 vertCount[4]; u16* vertsBlend;}` (`T4H:423-427`).
- T5/T6: the same plus `float* tensionData` at +0x0C (`T5H:458-463`, `T6H:2724-2729`). tensionData is ignored for

**XSurfaceFlag**, T5 (`T5H:529-536`) and T6 (`T6H:2716-2722`) **[V]**:

|---|---|---|

  **[V]**.
- **[!] Unknown:** what QUANTIZED or STREAMED do to `verts0`. OAT reads `xyz` as plain floats regardless. Treat a
  surface with STREAMED set (T5) and a null `verts0` as missing data **[I]**.

### 2.2 Vertex ordering inside a surface

OAT lays out a surface's `verts0` as follows (`XMC:432-560`) **[V]**:

1. **Rigid verts first.** One block per `vertList[k]`, in order. Each block has `vertList[k].vertCount` vertices, all
   bound to one bone.
2. **Then blended verts, by weight count:** `vertInfo.vertCount[0]` one-bone verts, then `[1]` two-bone, `[2]`
   three-bone and `[3]` four-bone verts.
3. **Anything left over** (up to `vertCount`) has no weights.

In shipped data a surface has one or the other: either `vertList` (rigid) or `vertsBlend` (deformed). See the asserts above.

### 2.3 Triangle indices

- **Indices are local.** `triIndices[t].i[0..2]` index the surface's own `verts0`.
  - OAT builds one vertex buffer per LOD and offsets each surface's indices: by `baseVertIndex` on T5/T6, and by the
    running sum of earlier surfaces' `vertCount` on T4 (`XMC:576-584`) **[V]**.
  - The T4 comment there, "T4 tri indices are local to the surface, while baseVertIndex does not match", shows that
    T4's `baseVertIndex` is not that offset.
  - **For E115:** keep one VB/IB per surface and use the indices as they are, in all three games **[I]**. This follows
    from the above.
- **Winding.** OAT reverses the index order when converting to glTF's right-handed space
  (`OAT/ObjWriting/XModel/Gltf/GltfWriter.cpp:56-63`) **[V]**. The source winding is the D3D convention for CoD's Z-up
  left-handed space.
- **T4 and IW3 quirk.** Some LOD0 surfaces have one triangle that no vert list covers (`XMC:212-218`) **[V]**.
  Harmless for rendering.

## 3. GfxPackedVertex and how to decode it

### 3.1 Layout: identical in all three games

| off | field | type |
|---|---|---|
| 0x00 | xyz | float[3] (model space, CoD units, Z up) |
| 0x0C | binormalSign | float (±1) |
| 0x10 | color | `GfxColor` (u32 / u8[4]) |
| 0x14 | texCoord | `PackedTexCoords` (u32) |
| 0x18 | normal | `PackedUnitVec` (u32) |
| 0x1C | tangent | `PackedUnitVec` (u32) |

- **Size:** 32 B (`type_align(16)`).
- **Definitions [V]:** `T4H:413-421`, `T5H:482-490`, `T6H:5744-5752`.
- **T6 cross-check [V]:** the stock T6 D3D11 PACKED input layout is pos s0:0 R32G32B32A32 (w = binormal sign), colour
  s0:16 RGBA8_UNORM, uv s0:20 **R16G16_FLOAT**, normal s0:24 and tangent s0:28 **R10G10B10A2_UNORM**
  (`RE/games/t6-bo2/notes/t6_techniques.md:173`).

**[!] Same layout, different encoding.** `bo1_to_bo2_porting.md:108` calls GfxPackedVertex "✅ identical". That is
true of the layout only. The texcoord half order and the unit-vector encoding both differ between T4/T5 and T6
(below). `sizes.txt:6` has no T5 size measured.

### 3.2 Which decode each game uses

The game wrappers are `OAT/Common/Game/T4/CommonT4.cpp:22-35`, `.../T5/CommonT5.cpp:22-35` and
`.../T6/CommonT6.cpp:25-38` **[V]**.

| | T4 (WaW) | T5 (BO1) | T6 (BO2) |
|---|---|---|---|
| texCoord | `Vec2UnpackTexCoordsVU` | `Vec2UnpackTexCoordsVU` | `Vec2UnpackTexCoordsUV` |
| normal / tangent | `Vec3UnpackUnitVecScaleBased` | `Vec3UnpackUnitVecScaleBased` | `Vec3UnpackUnitVecThirdBased` |
| color | `Vec4UnpackGfxColor` | same | same |

**T4 and T5 decode identically. T6 differs in texcoords and unit vectors.**

### 3.3 Formulas (`PACK` = `OAT/Common/Utils/Pack.cpp`)

**Texcoords: two IEEE half floats.**

- **T4/T5, "VU"** (`PACK:118-125`) **[V]**: `u = half(packed >> 16)` and `v = half(packed & 0xFFFF)`.
- **T6, "UV"** (`PACK:109-116`) **[V]**: `u = half(packed & 0xFFFF)` and `v = half(packed >> 16)`. This fits
  R16G16_FLOAT, where R is the low half.
- **The half decoder.** `HalfFloat::ToFloat` (`OAT/Common/Utils/HalfFloat.cpp:3-18`) is a bit-trick decoder.
  - Checked by brute force against numpy float16 for all 61,440 normal and negative half values: identical
    **[V-calc]**.
  - Zero maps to 0. Denormals, Inf and NaN were not checked. They don't occur in UVs **[I]**.
- **UV origin.** OAT writes UVs to glTF unchanged (`GltfWriter.cpp:603-604`) **[V]**. glTF and D3D share a top-left
  UV origin, so no V flip is needed for D3D-style or Vulkan sampling. Flip V (`1 − v`) only for a GL-style bottom-left
  origin **[I]**.
- **[!] T4/T5 half order not checked in game.** That T4/T5 store u in the high half is OAT's claim alone. It is
  supported by OAT GLB exports of BO1 maps looking right in our earlier BO1 → BO2 porting work **[I]**, but not checked against the
  D3D9 vertex decl.

**Normal and tangent on T4/T5: "scale based" UBYTE4** (`PACK:127-136`) **[V]**:

```
b = bytes of packed (b[0] = low byte)
scale = (b[3] + 192) / 32385          // 32385 = 127 * 255
n = ((b[0] - 127) * scale, (b[1] - 127) * scale, (b[2] - 127) * scale)
```

- **Second source [V].** The BO1/WaW vertex programs decode the same way: `UBYTE4 * 1/127 − 1`, with `0.752941`
  (192/255) as the sign/scale term (`RE/games/t6-bo2/notes/t6_techniques.md:197,314-315`). Expanded, that is exactly
  the formula above.
- **Normalising.** The result isn't exactly unit length. Normalise after decoding **[I]**.

**Normal and tangent on T6: "third based" signed 10:10:10** (`PACK:138-151`) **[V]**:

```
for c in 0..2:  x = (packed >> (10*c)) & 0x3FF
                v.u = x - 2*(x & 0x200) + 0x40400000      // build float 3.0 + s * 2^-22
                n[c] = (v.f - 3.0) * 8208.0312
```

- **Simplified:** `s` is the 10-bit field read as **two's-complement signed** (−512..511), and `n[c] = s / 511.0`,
  because 8208.0312 × 2⁻²² = 1/511.0 **[V-calc]**.
- **Top 2 bits.** Bits 30-31 are ignored. OAT's packer writes 0 there (`PACK:86-97`).
- **[!] Don't decode as UNORM.** The D3D11 layout feeds this to the shader as R10G10B10A2_UNORM, which only means the
  T6 shader decodes it itself (`t6_techniques.md:198`). Do **not** use `unorm * 2 − 1`. It gives wrong signs. Upload
  it as `A2B10G10R10_SNORM` (Vulkan) or `R10G10B10A2_UINT` and decode in the shader, or decode on the CPU **[I]**.

**Colour** (`PACK:153-159`) **[V]**, identical across games: `rgba = (b[0], b[1], b[2], b[3]) / 255`, byte 0 = red.
For T6 this matches RGBA8_UNORM **[V]**. **[!]** On T4/T5 (D3D9) the decl may be D3DCOLOR, which is BGRA in memory.
OAT assumes RGBA there too. Not checked. If BO1/WaW vertex colours come out with red and blue swapped, this is why **[I]**.

**Tangent frame.**
- OAT never exports the tangent or `binormalSign` (glTF vertex = position, normal, uv: `GltfWriter.cpp:22-27`).
- Decode the tangent with the same function as the normal **[I]** (same type, same input-layout format on T6).
- Then `bitangent = cross(normal, tangent) * binormalSign` **[I]**. The cross-product order is the usual CoD one.
  Check it on one normal-mapped model.

**Coordinate system.**
- CoD is Z-up and left-handed. OAT's glTF conversion is `(x, y, z) → (x, z, −y)` for positions and normals, plus
  −90° about X for quaternions (`GltfWriter.cpp:34-54`) **[V]**.
- glTF units are left as CoD units (inches) **[V]**: no scale is applied there.

## 4. Bones and skinning

### 4.1 Skeleton arrays

**Parents** (`XMC:260-263`) **[V]**. For `i ≥ numRootBones`:

```
parent = i - parentList[i - numRootBones]
```

Each entry is a **relative backwards offset**, so parents always precede children. Root bones (`i < numRootBones`)
have no parent.

**Local pose** (`XMC:280-301`) **[V]**:
- **Root bones** use the identity.
- **Non-root bone `i`:**
  - `trans[(i - numRootBones)*3 + 0..2]` are floats.
  - `quats[i - numRootBones].v[0..3]` are **int16 x, y, z, w**, each divided by 32767 (`QuatInt16::ToFloat`,
    `OAT/Common/Utils/QuatInt16.cpp:8-11`) **[V]**.

**Bind pose** (`XMC:269-278`) **[V]**:
- `baseMat[i]` (`DObjAnimMat {vec4 quat; vec3 trans; float transWeight}`, 32 B) is the bone's **model-space**
  ("global") bind transform.
  - Definitions: `T4H:352-357`, `T5H:451-456`, `T6H:2709-2714`.
- **transWeight** is `2 / |quat|²`, as OAT's loader writes it (`OAT/ObjLoading/XModel/LoaderXModel.cpp.template:263-271`)
  **[V]**. So `quat` may be unnormalised. Normalise it before building a matrix **[I]**. glTF's node path does
  normalise (`GltfWriter.cpp:344`).
- **How OAT's glTF uses it.** OAT's glTF output uses **only baseMat**. It gets each node's local transform as
  `inverse(parentGlobal) * global` (`GltfWriter.cpp:312-349`) and the inverse bind matrices as
  `inverse(T(baseMat.trans) * R(baseMat.quat))` (`GltfWriter.cpp:660-689`) **[V]**.
- **For E115:** use `baseMat` for the bind pose. Use `quats`/`trans` only when you need local channels (for XAnim
  playback). Then the check `world(parent) * local == baseMat` should hold **[I]**.

### 4.2 Bone references are byte offsets into a DObjSkelMat array

- **The divisor.** `XRigidVertList.boneOffset` and the bone entries of `vertsBlend` are **byte offsets**. Bone index =
  value / `sizeof(DObjSkelMat)` = value / **64** (`XMC:461,484,496-538`) **[V]**.
  - `DObjSkelMat {float axis[3][4]; float origin[4]}` is 64 B (`T4H:346-350`, `T5H:445-449`, `T6H:529-533`).
  - OAT's loader writes `boneIndex * sizeof(DObjSkelMat)` (`LoaderXModel.cpp.template:615,674,692`) **[V]**.

### 4.3 Rigid vertex lists (`XRigidVertList`, 12 B, the same in all games)

`{u16 boneOffset; u16 vertCount; u16 triOffset; u16 triCount; XSurfaceCollisionTree* collisionTree}`
(`T4H:387-394`, `T5H:520-527`, `T6H:5754-5761`) **[V]**.

- **Coverage.** List `k` covers the next `vertCount` vertices of `verts0` (section 2.2). All of them have weight 1.0 on
  bone `boneOffset / 64`.
- **triOffset/triCount** select that list's triangles (for its collision tree).
- **Vertices are in model space, not bone space.**
  - **Evidence:** OAT copies `verts0[i].xyz` straight to the output with no per-bone transform (`XMC:372-379`)
    **[V]**. It gives glTF inverse bind matrices built from `baseMat` (above).
  - **The reverse direction too:** OAT's loader writes model-space coordinates straight into `xyz`
    (`LoaderXModel.cpp.template:486-488`) **[V]**.
  - Those GLBs display correctly and round-trip through the BO2 linker in our earlier porting work **[I]**. That would not work if
    rigid verts were bone-relative.
  - **For a static draw:** render `xyz` directly, with no base-pose transform needed.
  - **For an animated draw:** the skinning matrix of bone `b` is `animWorld[b] * inverse(baseMatWorld[b])`. That is the
    usual inverse-bind setup, and it is what `DObjSkelMat` holds at runtime **[I]**.
- **"Default armature".** One bone, one root, every surface one vertList with boneOffset 0, triOffset 0 and all verts
  covered. OAT drops the skeleton for these (`XMC:194-236`) **[V]**. E115 can treat them as static meshes.
  - The T4 variant skips the triCount check (`XMC:212-218`) **[V]**.

### 4.4 vertsBlend layout (u16 stream, consumed in order) (`XMC:471-550`) **[V]**

| group (count) | u16 per vertex | layout | weights |
|---|---|---|---|
| `vertCount[0]` | 1 | `b0` | w0 = 1 |
| `vertCount[1]` | 3 | `b0 b1 w1` | w1 = w1/65535, w0 = 1 − w1 |
| `vertCount[2]` | 5 | `b0 b1 w1 b2 w2` | w0 = 1 − w1 − w2 |
| `vertCount[3]` | 7 | `b0 b1 w1 b2 w2 b3 w3` | w0 = 1 − w1 − w2 − w3 |

- `bN` are byte offsets, so divide by 64. Weights are u16, divided by 65535 (`XMC:427-430`).
- **Size.** The stream holds `1·c0 + 3·c1 + 5·c2 + 7·c3` u16 values.
- **Which vertices.** The groups apply to the vertices that follow the rigid lists (none, in practice), in group order.
- **Per-game differences:** none. The struct and this code are shared by T4, T5 and T6 **[V]**.

### 4.5 Limits worth knowing

- **Joint indices.** numBones is a u8, so ≤ 255 bones. glTF joints are written as u8 (`GltfWriter.cpp:644`).
- **Vertex limits.** The BO2 linker path we used for porting enforces ≤ 32,767 verts for animated models and ≤ 65,535 for rigid
  (`bo1_to_bo2_porting.md:117-119`). Indices are u16 per surface anyway.

### 5.4 Picking colour, normal and specular maps (OAT's heuristic, `XMC:54-173`) **[V]**

| | candidates | if more than one candidate |
|---|---|---|
| **Colour** | T4: semantic 2 only. T5/T6: semantic 2 **or** 0xC-0x1B | prefer nameStart/End `c…p` (`colorMap`), then `r…k`, then `d…p`, else the first |
| **Normal** | semantic 5 | prefer `n…p` (`normalMap`), else the first |
| **Specular** | semantic 8 | prefer `s…p` (`specularMap`), else the first |

**Recommendations for E115 [I]:**
- Take the same approach, but on T5/T6 rank semantic 2 above COLOR0-15. The COLORn slots hold camo and detail layers.
- For exact matches, compare `nameHash` with `R_HashString("colorMap")` and friends.

**R_HashString is djb2 with xor and `| 0x20` in all three games.** The formula is `h = h*33 ^ (c | 0x20)`, starting
from 0 (`OAT/Common/Game/T4/CommonT4.h:13-23`, `T5/CommonT5.h:37-47`, `T6/CommonT6.h:39-49`,
`OAT/Common/Utils/Djb2.h:72-82`) **[V]**. OAT tries to recover sampler names from it
(`MaterialJsonDumper.cpp.template:148-159`).

**[!] Disagreement over the T4 hash.**
- `RE/games/t6-bo2/notes/t6_techniques.md:307-308` says BO1 uses this T6 hash, "not WaW's lower-case djb2".
- OAT's T4 uses the same `| 0x20` variant.
- The two differ for non-letters. `'_'` (0x5F) becomes 0x7F under `| 0x20` but stays the same under `tolower`.
- If T4 nameHash lookups miss, try `djb2_xor_lower` (`Djb2.h:89`) or plain lower-case djb2. Rely on semantic plus
  nameStart/nameEnd, which don't depend on the hash.

### 5.5 Technique set and state bits

- **techniqueSet.** `techniqueSet->name` is the family E115 maps to its own shaders. Examples:
  - WaW/BO1 models `l_sm_*` / `mc_l_sm_*`, world `wc_l_sm_*`;
  - BO2 `lit_sm_*` / `mc_lit_sm_*` / `wc_lit_sm_*_<hash>`;
  - BO1 `*_unlit_replace`, WaW `*_unlit`.
  - Sources: `bo1_to_bo2_porting.md:123-126`, `t6_techniques.md:311-313` **[V]**.
- **MaterialTechniqueSet** `{name; worldVertFormat; ...; techniques[N]}` **[V]**:

  | game | techniques[N] | source |
  |---|---|---|
  | T4 | 59 | `T4H:1553-1560` |
  | T5 | 130 | `T5H:1785-1791` |
  | T6 | 36 | `T6H:803-808` |

- **stateBitsEntry.**
  - `stateBitsEntry[techType]` is an index into `stateBitsTable` (one entry per technique type) **[I]**. 0xFF probably
    means unused **[I]**.
  - The useful technique types (`T4H:1472-1479`, `T5H:1630-1639`, `T6H:746-751`) **[V]**:

    | technique | T4 | T5 | T6 |
    |---|---|---|---|
    | UNLIT | 4 | 4 | 2 |
    | LIT (LIT_BEGIN) | 8 | 0xA | 4 |

  - The full T6 list and the BO1/WaW → T6 mapping are in `t6_techniques.md` §1 and §3.
- **GfxStateBits.**
  - T4/T5: `loadBits.raw[2]`, 8 B.
  - T6: the same plus three D3D11 state pointers, 20 B (`T6H:3003-3009`).
  - **Word 0:** srcBlendRgb:4, dstBlendRgb:4, blendOpRgb:3, alphaTestDisabled:1, alphaTest, cullFace:2 (bits 14-15),
    srcBlendAlpha:4, dstBlendAlpha:4, blendOpAlpha:3, colorWriteRgb, colorWriteAlpha, polymodeLine (bit 31).
  - **Word 1:** depthWrite (bit 0), depthTestDisabled, depthTest:2, polygonOffset:2, then stencil fields.
  - Sources: `T4H:807-845`, `T5H:1004-1042`, `T6H:2957-2996` **[V]**.
  - **[!] alphaTest differs by game.**

    | game | alphaTest field | values |
    |---|---|---|
    | T4 | 2 bits (12-13) | 1 GT_0, 2 **LT_128**, 3 GE_128 (`T4H:676-678`) |
    | T5 | 2 bits (12-13) | 1 GT_0, 2 **GE_255**, 3 GE_128 (`T5H:882-884`) |
    | T6 | **1 bit** (12), bit 13 unused | 0 GT_0, 1 GE_128 (`T6H:2904-2905`) |

    The converter's earlier "ge255→ge128" bug came from this.
  - **Shared enums.** Cull values are 1 none, 2 back, 3 front in all three. Blend factors (0 disabled, 1 zero, 2 one,
    5 srcalpha, 6 invsrcalpha, ...) are shared (`T4H:645-687`, `T5H:853-893`, `T6H:2873-2914`) **[V]**.
- **Constants.** `MaterialConstantDef {u32 nameHash; char name[12]; vec4 literal}`, 32 B, 16-aligned, the same in all
  three (`T4H:857-862`, `T5H:846-851`, `T6H:2866-2871`) **[V]**.
  - `name` is truncated to 12 characters.
  - OAT recovers the full name when `R_HashString(name) == nameHash` or from a known-names table
    (`MaterialJsonDumper.cpp.template:192-208`) **[V]**.
  - Useful ones to read: colour tint, specular and gloss parameters. These are per-techset, so look them up by
    name/hash **[I]**.
- **cameraRegion.**
  - T4/T5: 0 lit, 1 decal, 2 emissive.
  - T6: 10 values (lit opaque/trans/quasi-opaque, emissive opaque/trans/fx, light map, depth hack, ...).
  - Sources: `T4H:1054-1062`, `T6H:670-685` **[V]**. A cheap opaque/translucent/emissive bucket hint.

### 6.2 GfxImageLoadDef: the in-zone pixel blob

| | T4 | T5 / T6 |
|---|---|---|
| levelCount (char) | +0 | +0 |
| flags (char, IWI flags) | +1 | +1 |
| dimensions u16[3] | +2 | – (use image width/height/depth) |
| format | int +8: **D3DFORMAT** | int +4: T5 **D3DFORMAT**, T6 **DXGI_FORMAT** |
| resourceSize | u32 +0xC | int +8 |

- Definitions: `T4H:1573-1581`, `T5H:1794-1801`, `T6H:3092-3099` **[V]**.
- How OAT reads it (`OAT/ObjWriting/Image/ImageToCommonConverter.cpp.template:80-123`) **[V]**:
  - **Size:** T4 takes it from `loadDef.dimensions`, T5/T6 from the GfxImage fields (`:89-93`).
  - **Format:** T4/T5 go through `Dx9TextureLoader`, T6 through `Dx12TextureLoader` (`:111-118`).
  - **Map type:** from the loadDef flags, using `IMG_FLAG_VOLMAP`/`CUBEMAP` for iwi6, iwi13 and iwi27 (`:103-108`).
  - **Mips:** present unless `IMG_FLAG_NOMIPMAPS` (bit 1) is set (`:120`).
- **Mip order in loadDef data:** largest to smallest (the `Dx9TextureLoader` default,
  `OAT/ObjImage/Image/Dx9TextureLoader.cpp:24`) **[V]**. QoS is the only reversed game.
- **IWI flag bits** per version (`OAT/ObjImage/Image/IwiTypes.h`) **[V]**:

  | IWI version | game | cube | vol | source |
  |---|---|---|---|---|
  | v6 | T4 | bit 2 | bit 3 | `IwiTypes.h:70-80` |
  | v13 | T5 | bit 2 | bit 3 | `IwiTypes.h:189-200` |
  | v27 | T6 | bit 2 | bit 3 | `IwiTypes.h:244-254` |

  The v8 entry (IW4/5, `IwiTypes.h:126-147`) uses map-type bits 16-17 instead.
- **[!] Missing formats.** OAT's Dx9 loader has no R5G6B5 or G16R16. BO1 lightmaps use them.
  - **Upstream behaviour:** `ImageDumper` skipped these silently.
  - **The fork's behaviour:** it now warns and writes `<image>.loaddef.bin`. The header is int[6]
    `{format, resourceSize, w, h, d, flags}`, followed by the raw data (`OAT/ObjWriting/Image/ImageDumper.cpp.template:107-128`,
    `bo1_to_bo2_porting.md:341-342`) **[V]**.
  - **For E115:** handle these D3D formats yourself.

### 6.3 Where the pixels live and how OAT finds them

The decision is `ImageToCommonConverter.cpp.template:163-171` **[V]**:

1. **In the zone.** If `texture.loadDef && loadDef->resourceSize > 0`, the pixels are in the fastfile. Decode the loadDef.
2. **T6 only: IPak.** If `streamedPartCount > 0`, look in each loaded IPak for the key
   `(nameHash = image.hash, dataHash = streamedParts[0].hash)`. The entry is a complete IWI v27 file (`:127-144`).
   - **Lookup:** IPak index entries are sorted by the combined key, and the search stops early
     (`OAT/ObjLoading/ObjContainer/IPak/IPak.cpp:61-75`).
   - **Which IPaks get loaded** (`OAT/ObjLoading/Game/T6/ObjLoaderT6.cpp:170-269`) **[V]**:
     - `base.ipak`, then `<lang>base.ipak`;
     - then `mp.ipak` + `so.ipak` for MP zones (`mp_*`, `*_mp`), `zm.ipak` for ZM zones, otherwise `sp.ipak`;
     - plus any IPak a KeyValuePairs asset names (namespace = zone-name hash, key = `IPAK_READ_HASH`).
   - **Only part 0 is read.** OAT reads only `streamedParts[0]`, and the struct only has room for one
     (`streamedParts[1]`). `GfxStreamedPartInfo` is `{levelCount:4, levelSize:28, hash, width, height, offset,
     size:28, ipakIndex:4, adjacentLeft:15, adjacentRight:15, compressed:1, valid:1}` (`T6H:826-840`).
3. **Otherwise, a loose .iwi.** Open `images/<name>.iwi` through the search path, with `*` in the name replaced by `_`
   (`OAT/ObjCommon/Image/ImageCommon.cpp:8-14`). The IWI version depends on the game: v6 for T4, v13 for T5, v27 for
   T6.
   - **IWDs are searched too.** Every `.iwd` (zip) in a search-path folder is mounted after the folder itself
     (`OAT/ObjCommon/SearchPath/SharedSearchPaths.cpp:15-53`).
   - **On T4/T5 this is the normal route** for images whose loadDef is empty or absent: point the search path at the
     game's `main/` (`iw_*.iwd`) or the mod folder **[I]**.
   - **BO1 maps:** zombie_theater.ff carries its 1318 images "in the ff itself" (`bo1_to_bo2_porting.md:51`) **[V]**.
4. **Not found:** the result is an error ("Could not find data for image") and a null texture.

**IWI pixel order:** **smallest mip first**, the opposite of loadDef.
- OAT reads mips from `mipMapCount − 1` down to 0 and checks the `fileSizeForPicmip[]` offsets as it goes
  (`OAT/ObjImage/Image/IwiLoader.cpp:84-102`, v6; the other versions are similar) **[V]**.
- **For E115:** use OAT's `image::LoadIwi` rather than writing your own reader.
- **The v27 header** is described in `t6_materials_runtime.md` (HUD icon section): magic `IWi`, version 27, u8 format,
  u8 flags, u16 w/h/d, float gamma, `maxGlossForMip[16]`, `fileSizeForPicmip[8]` at 0x20. The header is 64 B in total.

**[!] Streaming flags.**
- On T5/T6 the `streaming`, `delayLoadPixels`, `baseSize` and `pixels` fields are runtime state.
- Don't read pixels from `pixels` in a zone dump. Use only the loadDef / IPak / IWI routes above **[I]**.
